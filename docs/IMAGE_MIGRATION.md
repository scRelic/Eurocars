# Миграция изображений

Миграция не запускалась на рабочей базе и не удаляет локальные файлы.
Сначала проверьте её на копии базы и с отдельными тестовыми stores.
Примените актуальные 007–009 к тестовой базе только после проверки их
истории; рекомендации по существующей ранней 007 — в [BLOB_SETUP.md](./BLOB_SETUP.md).
Сохраните резервные копии базы и каталогов `.data`, а также исходных файлов
из `public/images`; зафиксируйте состояние до переноса.

Скрипт находит локальные фотографии с URL вида
`/api/cars/{carId}/images/{imageId}` и файлы `/images/...` внутри `public`,
а также локальные аватары `/api/users/{userId}/avatar/{token}`. Внешние URL
он не переносит. Пути вне доверенных каталогов, неподдерживаемые и
слишком большие файлы отклоняются. Файлы `public/images` уже доступны как
статические ресурсы: их перенос сам по себе не отзывает старую публичную
ссылку. Удаление или исключение таких исходников из будущего развёртывания
требует отдельного решения и проверки зависимостей.

Из корня `frontend`, с настроенными переменными окружения:

```powershell
# Без записи в Blob и без изменения БД; отчёт создаётся как новый файл.
node --env-file=.env scripts\migrate-images.ts --kind=listing --batch-size=20 --report=listing-dry-run.jsonl
node --env-file=.env scripts\migrate-images.ts --kind=avatar --batch-size=20 --report=avatar-dry-run.jsonl

# Только после подтверждения и проверки базы, stores, резервных копий и dry run:
node --env-file=.env scripts\migrate-images.ts --kind=listing --batch-size=20 --report=listing-batch-001.jsonl --apply
node --env-file=.env scripts\migrate-images.ts --kind=avatar --batch-size=20 --report=avatar-batch-001.jsonl --apply
```

Без `--apply` выполняются чтение и тестовая обработка Sharp. `--kind=all`
является значением по умолчанию и сначала выбирает фотографии, затем аватары.
`--batch-size` от 1 до 100. Для продолжения после ID используйте
`--kind=listing --after-id=123` или `--kind=avatar --after-id=123`.
В `all` курсор не поддерживается. Каждый `--report` создаёт новый JSONL-файл,
существующий файл не перезаписывается; для `--apply` он обязателен.

Запись `staged` содержит исходный URL и ID сессии до изменения ссылки;
`migrated` подтверждает применение, `sync-pending` означает сохранённую
ссылку и ещё ожидающую синхронизацию, `failed` требует проверки. Храните
отчёты с резервными копиями. При обрыве проверяйте актуальные строки БД по
ID и upload ID из журнала, не предполагайте, что отсутствие завершающей записи
означает отсутствие commit. Уже перенесённые строки не выбираются повторно.
Для повторной попытки ошибок перезапустите без курсора; для `sync-pending`
используйте `scripts\sync-listing-images.ts`. Ошибки дают ненулевой код.
Если ошибки занимают весь batch, используйте курсор для остальных записей,
затем повторите ошибочные отдельно. Объекты неуспешной подготовки попадают в
очередь очистки.

Операция прикрепления проверяет владельца и неизменность исходной ссылки;
аватар обновляется только если ссылка не изменилась во время переноса.
Исходник не удаляется. После прикрепления фотография черновика остаётся
приватной, ACTIVE получает публичную копию при синхронизации.

## План отката

1. Остановите мигратор и фоновые sync/cleanup-задачи, ограничьте запись в
   затронутые объявления и профили, сохраните текущую БД и JSONL-отчёты.
2. На отдельной копии восстановите исходные файлы и проверьте их доступность
   через старые локальные endpoints или static `public` на целевом сервере.
3. Из отчёта и резервной копии составьте список записей, которые не изменялись
   после переноса. Согласуйте и проверьте транзакционное восстановление ссылок
   и `storage_provider` с учётом ограничений схемы и блокировок приложения.
   Не перезаписывайте новые изменения пользователя. Для неоднозначных записей
   требуется ручная сверка, особенно если commit произошёл до записи результата.
4. Проверьте владельцев, порядок, главную фотографию и публичность. Только
   после этого возобновляйте приложение. Blob-копии не удаляйте автоматически:
   отдельно проверьте ссылки и очередь перед согласованной очисткой.

Выключение флагов само по себе **не** откатывает уже перенесённые данные.
