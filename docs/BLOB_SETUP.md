# Vercel Blob

Интеграция подготовлена за независимыми флагами `BLOB_AVATAR_ENABLED` и
`BLOB_LISTING_ENABLED`, по умолчанию оба `false`. Пока настоящие отдельные
тестовые Blob stores не проверены, не включайте флаги в production.
Локальная файловая система Vercel не является постоянным хранилищем:
отключённые флаги подходят для localhost, но не решают хранение в production.

## Хранилища и переменные

Создайте два **отдельных** Blob Store в Vercel: public для опубликованных
фотографий и аватаров и private для оригиналов, черновиков и обработки.
Режим доступа существующего store не переключается. Получите отдельные
read-write токены и настройте серверное окружение, не коммитьте `.env`:

```env
DATABASE_URL=postgresql://...
SESSION_SECRET=...
BLOB_READ_WRITE_TOKEN=...
BLOB_PRIVATE_READ_WRITE_TOKEN=...
BLOB_AVATAR_ENABLED=false
BLOB_LISTING_ENABLED=false
IMAGE_MAX_FILE_SIZE_MB=10
IMAGE_MAX_COUNT=20
IMAGE_MAX_WIDTH=1920
IMAGE_WEBP_QUALITY=82
IMAGE_THUMBNAIL_WIDTH=320
IMAGE_CATALOG_WIDTH=640
IMAGE_AVATAR_SIZE=256
```

Для localhost создайте отдельную тестовую базу и stores, настройте `.env`,
запустите `npm install` и `npm run dev`. Флаги включаются независимо после
проверки соответствующей миграции и тестов. Nitro читает токены только на
сервере; клиент получает ограниченный временный токен SDK, но не read-write
токен. Не добавляйте секреты в public runtimeConfig.

На Vercel задайте эти же секреты как Environment Variables соответствующего
окружения, подключите PostgreSQL Neon через `DATABASE_URL` с настройками TLS,
требуемыми Neon, и проверьте доступность private и public store. Выберите
Node.js runtime, не Edge. Не запускайте развёртывание или миграцию рабочих
данных без подтверждения. Размеры, операции и трафик влияют на расходы;
актуальные квоты и цены проверяйте на странице тарифов Vercel, а не по
оценке размеров в PostgreSQL.

## Схема и поток

Для существующей базы последовательно предусмотрены
`server/migrations/007_image_upload_sessions.sql` и
`server/migrations/008_listing_blob_images.sql`, затем
`server/migrations/009_complete_image_upload_sessions.sql`; для новой базы соответствующая
схема включена в `server/db.sql`. Перед применением сохраните резервную копию,
проверьте уже применённые миграции и сначала проверьте на копии базы.
Ранняя подготовительная версия 007 изменялась: если она уже применена, не
запускайте 007 повторно. Миграция 009 добавляет отсутствующие поля и таблицу
вариантов; перед применением всё равно сравните фактическую схему с ожидаемой.

API: `POST /api/uploads/prepare`, `POST /api/uploads/blob`,
`POST /api/uploads/complete`, `GET /api/uploads/:id/status`,
`DELETE /api/uploads/:id`, `GET /api/uploads/config`,
`POST /api/users/me/avatar/complete`, а также синхронизация одного фото
`POST /api/cars/:id/images/:imageId/sync`.
Существующие API объявлений и локальных изображений сохранены.

Браузер загружает оригинал напрямую в private store через SDK и ограниченный
токен. Авторизованный endpoint подтверждения независимо считывает объект и
проверяет его; серверный callback не используется, поэтому tunnel на
localhost не нужен. Origin/CSRF-проверки пользовательских запросов сохранены.
Sharp создаёт варианты один раз. В public store фотографии попадают только
после фиксации статуса ACTIVE; остальные выдаются через защищённый endpoint.
После отзыва публичного доступа уже скачанные и закешированные копии не
отзываются мгновенно.

## Очереди

После сохранения создаются задания синхронизации, а операции с объектами
заранее регистрируются в очереди очистки. PostgreSQL и Blob не имеют общей
транзакции. При ошибке исходные данные сохраняются, задания повторяются с
задержкой. Если браузер закрылся, отдельно запускайте конечные batch-задачи
по расписанию на доверенном Node.js worker, например Render или другом
планировщике. Бесконечный цикл внутри Vercel Function не нужен.

Команды выполняются из корня `frontend`; Node.js должен поддерживать запуск
TypeScript и `--env-file`. При необходимости передавайте переменные окружения
другим способом:

```powershell
node --env-file=.env scripts\sync-listing-images.ts --batch-size=20
node --env-file=.env scripts\cleanup-images.ts --batch-size=100
```

Обе команды по умолчанию только показывают задания. Флаг `--apply` разрешает
реальное копирование или удаление; используйте его только с проверенными
базой и токенами. Контролируйте ненулевой exit code и вывод. Очистка проверяет
ссылки, откладывает занятые объекты и повторяет ошибки; публичные кеши не
контролируются. Временный оригинал удаляется после истечения выданного токена,
а не немедленно: иначе ещё действующий токен мог бы загрузить его повторно.
Подробнее о переносе и откате — в [IMAGE_MIGRATION.md](./IMAGE_MIGRATION.md).

Если изображение не появляется, проверьте статус сессии, флаги, миграции,
наличие задания sync и настройки двух stores. Не выводите токены и полные
секретные строки подключения в журналы. Реальные прямые загрузки, включая
файлы больше 4,5 МБ, требуют отдельного сквозного теста с тестовыми stores.
Изолированный browser-тест проверяет включённые флаги, ошибки, повтор,
порядок фотографий, аватар и запрос на 5 МиБ с перехватом Blob API; это
**не** тест реального Vercel Blob. `tests/listings.integration.py` создаёт
временный PostgreSQL-кластер и запускает этот сценарий; для сокращённого
прогона задайте `E2E_IMAGE_ONLY=1` и `PG_BIN` с каталогом утилит PostgreSQL.

Документация SDK: [Vercel Blob](https://vercel.com/docs/vercel-blob),
[client upload](https://vercel.com/docs/vercel-blob/client-upload),
[private storage](https://vercel.com/docs/vercel-blob/private-storage),
[Blob SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk).
